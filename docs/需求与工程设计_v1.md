# 自媒体账号监控中台 · 需求理解与工程设计（v1 · 评审稿）

> 范围：第一阶段覆盖抖音、B 站、小红书、微信公众号四个平台。
> 本文只做需求、能力边界、信息架构、设计规范、技术方案与算法设计，**不含业务代码**。
> 调研时间：2026-11。平台开放政策变化极快，所有"能/不能"的结论都应在立项时二次核实。

---

## 0. 一页结论（先看这页）

### 0.1 这件事的本质

你要的不是"数据看板"，而是**一个能替你做判断的账号运营驾驶舱**：
每天用一屏回答三个问题——"我的号现在怎么样 / 昨天出了什么事 / 下一批内容该怎么改"。
数据采集只是地基，真正的产品价值在第三层：**把四个平台口径完全不同的指标，折算成可横向比较的分数，并给出可执行的改进动作**。

### 0.2 五条关键判断（会直接影响排期和预算）

| # | 判断 | 影响 |
|---|---|---|
| 1 | **抖音官方内容数据接口已对新建应用关闭**（`data.external.item` 自 2025-02-13 起停止申请，旧应用存量可用，接口已实际下线） | 抖音数据不能指望官方 API，必须走"浏览器插件读自己后台 / 第三方数据服务"二选一 |
| 2 | **抖音 Web 端自动发布基本不可得**（"发布内容至抖音"能力仅对创作工具/社区/硬件/游戏类应用开放，明确排除企业宣传与营销内容，且要求企业主体注册资本≥50 万、成立≥1 年） | 抖音只能"生成素材 + 人工发布 + 回填链接"，不要在产品里承诺一键发布 |
| 3 | **小红书没有面向普通开发者的笔记数据/发布接口**（开放平台定位是电商商家与服务商） | 小红书是四个平台里能力最弱的一环，建议第一期只做"手动登记 + 第三方数据" |
| 4 | **B 站开放平台不开放个人开发者入驻**（要求中国境内法人、营业执照、盖章申请公函），但接口本身质量最好（稿件投递、单稿数据、30 天增量） | 有企业主体就优先把 B 站做深，它是最"正规"的一条链路 |
| 5 | **公众号个人主体无法认证，等于没有发布与数据分析接口** | 若账号是个人订阅号，公众号模块只能靠"文章页抓取 + 手动录入"，发布必须人工 |

**一句话结论**：这个项目 70% 的工程量在"把拿不到的数据用合规方式补上"，30% 在界面和算法。立项前必须先确认一件事——**你手上有没有一个可用于申请开放平台的企业主体**。这一条决定了产品是做"自动化中台"还是做"半自动记账 + 分析台"。

### 0.3 与参考截图的关系

参考截图（仅本地留存，不随仓库分发）里右上角有四个状态灯：**守护进程运行中 / NAS 已挂载 / 专用浏览器在线 / 平台登录今日已检**。
这说明那套工具的真实采集方式大概率是：**本地守护进程 + 保持登录态的专用浏览器 + 本地存储**，而不是官方 API。
这个事实很重要——它验证了"浏览器侧采集"在工程上是可行的，也提示我们：**登录态健康度本身就是一个必须被监控的产品模块**（详见 §3.2 M0）。

## 1. 需求理解复述

### 1.1 用一句话讲清

> 一个人（或一个小团队）同时运营抖音、B 站、小红书、公众号四个账号，内容一稿多发；
> 现在需要一块 Web 中台，把四个平台散落在各自后台的数据收拢到一处，
> 用统一的评分体系判断"哪条内容真的好"，并把"下一步改什么"直接写出来。

### 1.2 业务闭环（这个产品到底嵌在哪一步）

```
选题 → 生产 → 一稿多发（发布编排） → 数据回流（采集） → 评分与归因（算法） → 改进建议（规则） → 下一轮选题
                    ↑                                                            │
                    └────────────────────────────────────────────────────────────┘
```

产品的差异化在第 4、5 步。如果只做 1–3 步，市面上有大量现成工具（新榜、蝉妈妈、各平台创作者中心），没有自建必要。
**自建的唯一理由：四个平台的指标口径必须被统一，且建议必须贴合"我自己的号"。**

### 1.3 目标用户与使用节奏

| 角色 | 什么时候用 | 看什么 | 停留时长 |
|---|---|---|---|
| 主理人（你） | 每天早上 | 第一屏：昨日总览 + 异常 + 今日待发 | 2–3 分钟 |
| 内容编辑 | 发布前 / 复盘会 | 单篇详情、素材版本、评分拆解、改进建议 | 10–20 分钟 |
| 复盘（周会） | 每周一 | 周对比、平台横向对比、Top/Bottom 内容 | 15 分钟 |

这决定了信息架构：**首页是"扫一眼"的，详情页才是"读下去"的**。不要把分析塞进首页。

### 1.4 关键假设（不成立就要改方案）

1. 账号是**自有账号**，不是替客户代运营（否则涉及多租户与授权链条，工作量翻倍）。
2. 内容以**一稿多发**为主，四平台内容存在可对齐的"同一作品"关系（否则无法做跨平台对比）。
3. 数据延迟容忍度是 **T+1**，不要求分钟级实时（实时会显著抬高采集成本与风控风险）。
4. 发布频率在**每天 1–5 条**量级，不是矩阵号批量作业（后者需要另一套反封控设计）。
5. 可以接受**部分模块先人工录入**，不追求第一天就全自动。

### 1.5 歧义与待拍板清单（按重要性排序）

| # | 问题 | 为什么必须现在定 | 我的建议默认值 |
|---|---|---|---|
| Q1 | **是否是唯一使用者？** 未来会不会给团队/客户开账号？ | 决定要不要做多租户、RBAC、数据隔离，成本差 30%+ | 先做单租户 + 简单角色，但数据库预留 `tenant_id` |
| Q2 | **有没有可用于申请开放平台的企业主体？**（营业执照、可盖章） | 决定 B 站/抖音/公众号能不能走官方链路 | 有 → 优先 B 站；没有 → 全走浏览器采集 |
| Q3 | **四个账号是否都是本人/本公司主体？** | 授权链条合法性，尤其是抖音与小红书 | 必须是自有或已获书面授权 |
| Q4 | **能否接受"半自动发布"？**（系统生成素材包 + 到点提醒，人工点发布） | 决定要不要做发布队列的复杂状态机 | 第一期接受半自动，只对公众号/B 站做全自动 |
| Q5 | **预算量级？**（是否愿意为第三方数据付费） | 小红书几乎只能买数据；蝉妈妈等企业版 API 是年费制 | 预留每年 1–3 万元数据采购预算，否则小红书模块只能是手工 |
| Q6 | **是否需要粉丝画像？** | 画像数据几乎全部来自各平台后台页面，官方接口覆盖极差 | 第一期只做"能拿到的画像快照"，不做画像趋势 |
| Q7 | **"流量来源"是否为核心需求？** | 只有抖音/小红书/公众号后台有，且无 API | 用浏览器采集兜底；拿不到就在 UI 上明确标注"本期不可得" |
| Q8 | **评分是否要对内考核？** | 一旦用于 KPI，就必须可解释、可申诉、防作弊 | 第一期定位"诊断工具"，不用于绩效 |
| Q9 | **是否需要竞品/对标账号监控？** | 这是完全不同的采集对象（他人数据，合规风险更高） | 第一期不做 |
| Q10 | **数据保留多久？** | 影响存储选型与成本 | 明细 2 年，日聚合永久 |

> 建议评审会上只拍 Q1、Q2、Q4、Q5 四条，其余可按默认值推进。

### 1.6 明确的非目标（第一期不做）

- 不做内容自动生成（选题/文案/剪辑）。
- 不做投放（DOU+、薯条、B 站起飞）的 ROI 归因。
- 不做竞品监控与行业榜单。
- 不做移动端 App（响应式 Web 即可）。
- 不做分钟级实时数据。
- 不做多租户 SaaS 化售卖。

## 2. 四平台能力矩阵

### 2.1 能力分级定义

| 级别 | 含义 | 产品含义 |
|---|---|---|
| **A 官方可得** | 有正式开放平台接口，申请通过后可稳定调用 | 可做成自动、可持续的产品功能 |
| **B 后台可见但无接口** | 平台创作者后台能看到，但没有对外 API | 只能靠浏览器侧采集（读自己登录态的页面） |
| **C 仅第三方/逆向** | 无任何官方途径，只能买第三方数据或逆向接口 | 合规风险高，建议不做或只做人工登记 |
| **D 不可得** | 连后台都没有 | UI 上明确不做 |

### 2.2 总表（★ = 建议第一期实现）

| 维度 | 抖音 | B 站 | 小红书 | 微信公众号 |
|---|---|---|---|---|
| 账号粉丝总数 | B（创作者中心）／小程序侧有"抖音主页数据"但限千粉以上 | **A**（开放平台账号/稿件体系）★ | C | **A**（认证号 `user/summary`）★ |
| 作品列表 | B | **A**（稿件列表）★ | C | **A**（已发布列表 `freepublish/batchget`，仅认证服务号）★ |
| 单篇播放/阅读 | B | **A**（`arcopen/fn/data/arc/stat`）★ | C | **A**（图文分析，仅认证）★ |
| 单篇互动（赞/评/藏/转） | B | **A**（转赞评、收藏、分享）★ | C | **A**（分享/收藏/在看/点赞）★ |
| 完播率 / 读完率 | B（创作者中心） | B | B | B（阅读完成率在后台） |
| 流量来源结构 | B | B | B | **A**（阅读来源，仅认证）★ |
| 粉丝画像 | B | B | B | **A**（用户画像，认证后可用）★ |
| 发布内容 | **基本不可得**（见 §2.3.1） | **A**（稿件投递 `video/add`，需权限+报备）★ | C（无公开 API） | **A**（草稿箱 + `freepublish`，仅认证服务号）★ |
| 定时发布 | 无 | **A**（投稿接口支持定时） | 无 | 部分（发布接口，需自建调度） |
| 内容审核 | 平台侧机审+人审，无前置审核接口 | 稿件提交后有审核期，期间不对外可见 | 机审+人审 | 发布前可调"内容安全接口"自检 |
| 主体资质 | 企业，注册资本≥50 万且成立≥1 年（发布能力） | **中国境内法人**（个人不可入驻） | 商家/服务商资质 | 企业主体 + 微信认证（300 元/年） |
| 申请周期（经验值） | 2 周–2 个月，且大概率被拒 | 2–6 周（含盖章公函、权限审批、业务报备） | 1–4 周（且拿不到内容接口） | 认证 1–5 个工作日；接口权限即时开通 |
| 限流 | 按接口配额，超限报错 | 按应用配额 + 白名单机制 | — | 按账号类型有日调用上限，每月 10 次清零机会 |

### 2.3 分平台详解

#### 2.3.1 抖音 —— 能力最"看起来多、实际最窄"

**官方能给什么**
- 登录授权（OAuth）、用户公开信息（昵称、头像、粉丝数等基础字段）。
- 内容管理：视频上传、创建视频（`video-management` 系列），但**依附于"发布内容至抖音"能力**。
- 数据：曾经有 `data.external.item`（视频数据）与 `data.external.user`（用户数据），**2025-02-13 起停止新申请**，且社区反馈接口已下线、暂无替代。
- 小程序路径下另有"抖音主页数据""视频数据查询"能力，但要求：小程序已上线、企业主体、信用分 > 90、仅返回千粉以上账号，且需要用户在小程序内完成抖音授权。**对一个纯 Web 中台来说，为了拿数据去养一个小程序，不划算。**

**发布为什么基本走不通**
2025-08-19 公告明确收紧了"发布内容至抖音"：不再向个体工商户开放；企业需注册资本 ≥ 50 万且成立 ≥ 1 年；仅对**创作工具、社区、硬件配套、游戏类**应用开放；使用场景仅限 C 端用户创作后的分享，**企业宣传、商品介绍、诱导分享等营销内容不开放**。
一个"自家账号运营中台"既不属于上述应用类型，内容也属于品牌宣传——**准入逻辑上就不匹配**。即便申请到 H5 扫码投稿（网页生成二维码，用户用抖音 App 扫码后进入编辑页），也无法做到无人值守发布。

**结论**：抖音 = **数据靠浏览器采集，发布靠人工**。产品上要做的是"把发布这件事变得只要 30 秒"（素材包、文案、话题、封面一键复制 + 发布后回填链接），而不是"自动发"。

#### 2.3.2 B 站 —— 唯一可以做"正统自动化"的平台

**官方能给什么（质量最好）**
- 稿件投递：`member.bilibili.com/arcopen/fn/video/add`、文章提交 `arcopen/fn/article/add`（Scope `ARC_BASE`/`ATC_BASE`，需用户授权）。
- 稿件数据：单稿 `arcopen/fn/data/arc/stat`（转赞评、收藏、分享），整体稿件近 30 天增量数据。
- 上传：分片上传（`part/init`、`part/upload`、`part/complete`），有沙盒环境可联调。
- 稿件提交后有审核期，期间不对外可见——这要求发布状态机必须处理"已提交未过审"的中间态。

**门槛**
- **暂未开放个人开发者入驻**；要求中国境内合法存续法人、营业执照、盖章申请公函。
- 应用创建后要逐个接口申请权限，填写理由；部分业务还需邮件报备、配置 `biz_code`。
- 有白名单机制（按 UID 限制调用），适合"只服务自己的号"这种场景，反而是优点。

**结论**：有企业主体 → **B 站是第一期唯一值得做全自动（采集 + 投稿 + 数据回流）的平台**，也是验证整条链路的样板。

#### 2.3.3 小红书 —— 四平台里最弱的一环

**官方能给什么**
- 开放平台（`open.xiaohongshu.com`）定位非常明确：**电商**。应用类目是"工具型应用（ERP、打单、搬家上货、进销存）"和"自用型应用（店铺自研）"，接口围绕商品、订单、物流、售后、带货达人结算。
- **没有面向普通开发者的笔记发布、笔记数据、评论、粉丝画像接口。**
- 蒲公英（达人商业合作平台）的数据只在蒲公英后台可见，不对外开放标准 API。

**现实中的三种做法**
1. **人工登记**（推荐第一期）：发布后在系统里填链接，系统抓取公开笔记页的点赞/收藏/评论数（公开页面，低频、可控）。
2. **第三方数据服务**：市面上存在逆向蒲公英/笔记接口的商用 API（按次计费），能拿到粉丝画像、笔记表现、涨粉历史。**本质是破解签名，属于高风险**，且随时断供。
3. **浏览器插件读自己后台**（创作者中心）：合规性最好，但页面结构变动频繁，维护成本高。

**结论**：小红书第一期只做"手动登记 + 公开页低频抓取 + 评分"，发布明确标注"需人工"。**不要在产品里给小红书承诺任何自动化。**

#### 2.3.4 微信公众号 —— 接口最完整，但被主体类型卡死

**官方能给什么（认证服务号/企业认证订阅号）**
- 用户分析：`datacube/getusersummary`、`getusercumulate`（粉丝增减、累计）。
- 图文分析：`getarticlesummary`（单篇阅读）、`getuserread`、`getuserreadhour`（分时）、转发/分享数据。
- 消息分析、接口分析。
- 素材管理 + 草稿箱 + 发布：`draft/add` → `freepublish/submit`，可查已发布列表 `freepublish/batchget`。
- 用户画像（性别/年龄/地域/终端），认证后可用。
- 阅读来源（公众号会话/朋友圈/搜一搜/看一看/其他）——**四平台里唯一能通过 API 拿到流量来源结构的**。
- 内容安全接口：发布前可自检违规词/图片。

**致命限制**
- **个人主体公众号无法微信认证**（2014-08-26 后注册的个人订阅号不支持），因此拿不到上述绝大部分接口。
- `freepublish` 系列**仅服务号且非个人主体已认证**可调用；社区大量 48001 报错都是这个原因。
- 有日调用上限，每月 10 次清零机会。

**结论**：企业认证服务号 → 公众号模块可以做到接近全自动（含定时发布、来源分析、画像）；个人订阅号 → 只能"文章页抓取阅读数 + 手动录入"，发布纯人工。

### 2.4 三条技术路线的对比（这是本项目的核心决策）

| | A. 官方开放平台 | B. 浏览器侧采集（自有登录态） | C. 第三方数据服务 / 逆向接口 |
|---|---|---|---|
| 覆盖平台 | B 站、公众号（认证） | 四个平台都能覆盖 | 抖音、小红书为主 |
| 稳定性 | 高（有版本化、有公告） | 中低（页面改版即失效） | 低（随时断供、封号） |
| 合规性 | 高 | **中高**（自己的账号、自己的数据、自己的浏览器） | **低**（违反平台协议，有法律风险） |
| 成本 | 申请成本高、调用成本低 | 开发维护成本高 | 按量付费，长期贵 |
| 数据粒度 | 受接口限制（往往缺画像、缺来源） | 最全（后台有什么就能拿什么） | 较全 |
| 封号风险 | 无 | 低（模拟人工频率） | 中高 |
| 建议占比 | B 站、公众号为主 | **兜底主力** | 仅小红书补位，且要能一键切换 |

**合规红线（必须在文档里写死）**
- 只采集**自己拥有或已获书面授权**的账号。
- 不绕过登录、不破解签名、不使用他人 Cookie、不采集他人隐私数据（画像只到聚合维度）。
- 采集频率对齐人工浏览节奏（单账号每日个位数到几十次请求），不做并发轰炸。
- 第三方服务仅作为可替换的数据源，合同中要求对方承诺数据来源合法，并在 UI 标注"第三方数据，仅供参考"。
- 参考判例方向：平台用户协议普遍禁止自动化抓取；已有"刷宝"类不正当竞争判例。**自用、低频、自有账号**是降低风险的关键，但**不等于零风险**。

### 2.5 数据可得性对产品功能的直接影响（提前对齐预期）

| 功能 | 抖音 | B 站 | 小红书 | 公众号 |
|---|---|---|---|---|
| 粉丝趋势 | 可用（采集） | 可用（API/采集） | 仅手动/第三方 | 可用（API） |
| 单篇评分 | 可用（采集） | 可用（API） | 部分（公开页） | 可用（API） |
| 流量来源 | 仅采集，可能缺 | 仅采集 | 不可得 | **API 可得** |

## 4. 设计规范（从 bencho.dev 提炼，再落到本项目）

### 4.1 先说清楚一个判断

bencho.dev 是一个**极简组件库**：一个页面只讲一个交互，留白极大，视觉上几乎没有"装饰"。
你的参考截图是**高密度运营大屏**：一屏十几组数字。
两者不能直接照抄。**要移植的是"语法"（色、字、圆角、节奏、动效），不是"密度"。**
如果照搬 bencho 的留白，你的首屏会变成三屏；如果照搬截图的密度而不学 bencho 的秩序，就会变成"数据糊在墙上"。
**正确做法：用 bencho 的秩序去承载截图的密度。**

### 4.2 从参考站提取到的客观事实（不是印象）

以下数值来自实际抓取该站 CSS 与页面结构：

| 项 | 实测值 | 出现频次/说明 |
|---|---|---|
| 主文字/深色块 | `#17181a` | 全站最高频颜色（1300+ 次），是"黑"但不是纯黑 |
| 页面底色 | `#f7f7f6` | 暖白，不是纯白，纸张感 |
| 卡片/反白 | `#ffffff` | 纯白只用于浮起的卡片 |
| **唯一强调色** | `#2231dd` | 200+ 次，蓝紫，只用于选中/焦点/主行动 |
| 语义色 | 红 `#e5484d`、绿 `#1f9d55`、橙 `#e09a12` | 极少量使用 |
| UI 字体 | `Inter`（后备 Maison Neue / Instrument Sans / Helvetica） | `--font-ui` |
| 标题字体 | `Plus Jakarta Sans` / `Google Sans` | `--font-head` |
| 数字/代码 | `ui-monospace / SF Mono / Menlo` | `--font-code`；数字启用 `tabular-nums` |
| 圆角 | `999px`（胶囊）、`20px`（卡片）、`10px`（内块）、`6px`（标签） | 四档，不随意取值 |

| 结构 | 一个 block 一个"舞台"，说明文字小、灰、短 | 层级靠留白和字重，不靠边框和阴影 |

### 4.3 提炼成 8 条可复用规则

**R1 一个强调色。** 全站只有一个主强调色（蓝紫），其余全部是灰阶。平台品牌色（抖音黑、B 站粉蓝、小红书红、微信绿）**只允许出现在 8px 圆点、图标、或单平台图表系列**，不得用于按钮、标题、链接。
→ 截图里平台卡用了品牌色做 sparkline 描边，这可以保留，因为它承担"识别"功能而非"强调"功能。

**R2 暖白纸面 + 纯白浮层。** 页面底 `#f7f7f6`，卡片 `#ffffff`，**用 1px 透明边框 + 极淡阴影（`0 1px 2px rgba(23,24,26,.06)`）**区分层级，不用重描边。
→ 截图已经是这个路子，保持。

**R3 三个字号就够。** 页面里只允许三档：`28/20px`（数字与大标题）、`13–14px`（正文与指标名）、`11–12px`（辅助说明与时间戳）。**不许出现 16px、18px 这种中间档**——中间档是"层级模糊"的根源。
参考截图的层级其实是四档（大数字/卡片数字/标签/脚注），我们把它压到三档 + 一个"超大数字"特例（首屏总粉丝，40–48px）。

**R4 数字必须等宽。** 所有指标数字 `font-variant-numeric: tabular-nums`，字号变化时列不跳动。跨平台对比时尤其重要。
**R5 胶囊只给"可切换"的东西。** `999px` 圆角只用于 Tab、筛选、状态标签；卡片用 `20px`，内嵌小块用 `10px`。**不要把内容卡片做成胶囊**（会显得像按钮）。

**R6 图表的"节奏"来自间隙，不是颜色。** 堆叠柱固定 6px 间隙、柱宽随容器均分；同一系列只用同色系不同明度，不引入第三种色相。
→ 截图的堆叠柱用了四平台品牌色，视觉上是"彩条"，我建议改为**同一蓝色系四档明度 + 平台图例**，hover 时才点亮品牌色。这样整页更安静，也更符合 R1。

**R7 交互用"生长"和"环形高亮"，不用"淡入淡出"。** 切换周期（7 天/30 天）时柱子从基线生长；hover 时用 2px 环形描边锁定目标，tooltip 跟随鼠标但**垂直位置固定**，避免抖动。
→ 这一条直接决定"高级感"。默认的 tooltip 跟随鼠标 X/Y 会让整页显得廉价。

**R8 每块内容都要有"一句话结论"。** bencho 每个 block 下方都有一行小字说明它做什么。对应到中台：**每张图表右上角有一个"结论位"**（如"较上周 +12%，主要来自 B 站"），没有结论的图表不许上线。
→ 这是把"看板"变成"驾驶舱"的关键设计手法，也是截图右侧数据分析卡的价值所在。

### 4.5 每个模块的设计手法（含空态与异常态）

| 模块 | 图表/结构 | 信息密度 | 关键交互 | 空态 | 异常态 |
|---|---|---|---|---|---|
| **M0 连接健康度** | 4 个状态点 + 文字（运行中/在线/已检查），点击展开诊断抽屉 | 极低 | 点击看每个平台的"最后成功时间 / 失败原因 / 重连" | "尚未连接任何账号" + 主按钮「去连接」 | 红色点 + 顶栏横幅"抖音数据已 2 天未更新"，**并在所有受影响的数字旁打 ⚠ 角标** |

| **M5 规则洞察** | 竖向卡片列表，每条：结论句（14px 加粗）+ 证据（12px 灰）+ 标签（涨粉/互动/转化）+ 时间 | 高 | hover 展开"怎么算的"（指标、窗口、对比基准） | "数据不足，暂无法生成结论（需 ≥7 天数据）" | 规则命中但置信度低时加"样本少"标签 |

### 4.6 三条容易被忽略的细节

1. **环比永远要带基准。** 不写"播放 +12%"，要写"+12% vs 上周同期"。截图里的"比第 7 周日均（80）少 49%"就是好例子。
2. **"0" 和 "—" 必须区分。** 0 是真实值，— 是没数据。混用会直接摧毁信任。
3. **深色模式不是必须，但要留出接口。** bencho 的 Light/Dark 是组件级切换；我们的中台建议第一期只做浅色，但颜色全部走 token，后续可无痛加深色。

**为什么是 Python + Next.js**

### 5.2 采集层设计（本项目最重的部分）

#### 5.2.1 适配器契约（统一出口）

每个平台适配器必须实现同一组方法，**上层不感知平台差异**：

| 方法 | 作用 | 官方实现 | 浏览器实现 | 手动实现 |
|---|---|---|---|---|
| `auth_status()` | 授权/登录态是否有效 | 校验 token 有效期 | 打开后台，检查是否跳登录页 | 永远"人工确认" |
| `fetch_account()` | 账号快照（粉丝、作品数） | 调用户信息接口 | 读后台首页数字 | 用户填写 |
| `list_contents(cursor)` | 作品列表（增量） | 分页拉列表 | 读内容管理列表页 | 导入 CSV |
| `fetch_content_metrics(ids)` | 单篇指标 | 批量查（注意配额） | 逐条打开详情页 | 用户填写 |
| `fetch_traffic_sources()` | 流量来源 | 公众号有 | 后台数据页 | 不可得 |
| `fetch_audience()` | 画像快照 | 公众号有 | 后台画像页 | 不可得 |
| `publish(payload)` | 发布 | B 站/公众号 | ✕（明确不支持） | 生成"发布包"给人工 |

**关键设计**：`fetch_*` 返回的不是原始 JSON，而是 `NormalizedMetric`——包含 `platform / metric_key / value / unit / window / observed_at / source_type / confidence`。
`source_type ∈ {api, browser, manual, third_party}`，这个字段会一路透传到 UI，用于打标。

#### 5.2.2 增量拉取策略

- **列表增量**：以 `platform_content_id` 为游标，每次只拉"上次最大 ID 之后"的内容；同时按发布时间回溯 7 天做一次"补差"，防止置顶/删除导致的顺序错乱。
- **指标增量**：内容发布后的 **24h / 72h / 7d / 30d** 四个固定观察窗各拉一次（不是每天都拉全量）。
  理由：内容数据 90% 的价值集中在前 72 小时；固定窗口才能保证跨内容可比（见 §6.4 的时间对齐）。
- **账号级指标**：每天固定一次（粉丝、总播放），时间点固定（如 09:00），避免"今天 9 点、明天 23 点"造成的日增失真。
- **回补任务**：提供"按日期区间重跑"的能力，用于接口恢复/口径修正后重算。所有原始响应落 `raw_payload`，保证可重放。

#### 5.2.3 限流

三层限流，缺一不可：

1. **平台配额层**：每个平台每个应用一个令牌桶，容量与速率按官方文档配置（如公众号日上限、B 站 QPS），配置化而非硬编码。
2. **账号层**：单账号并发 ≤ 2，请求间隔加 300–1200ms 随机抖动（浏览器采集必须）。
3. **全局闸门**：全站同时运行的采集任务数上限，防止夜间批量任务把本机/代理打满。

触发限流时的行为：**退避而非重试风暴**——指数退避（1s→2s→4s→…→上限 5 分钟）+ 抖动，连续失败 5 次进入熔断（30 分钟内不再尝试该平台），并把 M0 状态灯变黄。

#### 5.2.4 失败重试与可观测

- 错误分类：`AUTH_EXPIRED`（需人工重新登录，**不自动重试**）、`RATE_LIMITED`（退避重试）、`NOT_FOUND`（内容被删，标记 `deleted`）、`PARSE_FAILED`（页面改版，告警）、`NETWORK`（重试）。
- 每次采集写 `collect_job`：`job_id / platform / account_id / type / started_at / finished_at / status / error_code / retry_count / payload_ref`。
- **数据质量看板**（隐藏但重要）：每个平台的"应采条数 vs 实采条数"、"最后成功时间"、"连续失败天数"。这是 M0 的数据来源。

### 5.3 存储选型与核心表

| 存储 | 选型 | 理由 |
|---|---|---|
| 主库 | PostgreSQL 16 | 事务、JSONB、扩展生态，单机足够撑到千万级指标 |
| 时序 | TimescaleDB（PG 扩展） | 不用引入第二套数据库；按 `observed_at` 分区、自动压缩 |
| 分析（可选） | ClickHouse | 仅在指标行数 > 5000 万 或 需要复杂多维聚合时引入，**第一期不要上** |
| 缓存/队列 | Redis | 缓存首页聚合、分布式锁、Celery broker |
| 对象存储 | S3/OSS/本地 NAS | 封面、后台截图（作为采集证据）、原始响应归档 |

**核心表（只列关键字段与唯一键）**

| 表 | 作用 | 唯一键 / 幂等键 |
|---|---|---|
| `platform_account` | 平台账号与授权 | `(platform, platform_account_id)` |
| `platform_credential` | token/登录态（加密） | `(account_id, credential_type)` |
| `content` | 作品（一条内容一行） | `(platform, platform_content_id)` |
| `content_variant` | 同作品跨平台映射 | `(work_id, platform)`，`work_id` 为人工/自动归并的"一稿" |
| `content_metric` | 单篇指标时序 | `(content_id, metric_key, window, observed_at)` |
| `account_metric` | 账号指标时序 | `(account_id, metric_key, stat_date)` |
| `traffic_source_daily` | 来源结构 | `(account_id, stat_date, source)` |
| `audience_snapshot` | 画像快照 | `(account_id, snapshot_date, dimension, bucket)` |
| `collect_job` | 采集任务 | `job_id` |
| `publish_task` | 发布任务 | `(content_version_id, platform)` + `idempotency_key` |
| `score_snapshot` | 评分结果（版本化） | `(content_id, window, algo_version)` |
| `insight` | 洞察结论 | `(rule_id, subject_id, window, generated_at)` |
| `raw_payload` | 原始响应 | `payload_id` + `(platform, endpoint, request_hash, fetched_at)` |

**一条重要原则**：**原始层永远不覆盖，标准层可以重算。**
平台口径一变（比如小红书把"阅读"改成"观看"），只要原始层还在，就能重跑历史，而不是从今天开始断档。

### 5.4 定时发布：任务队列与幂等

#### 5.4.1 状态机（每个平台一份，独立推进）

```
draft ──提交审核──> pending_review ──通过──> scheduled ──到点──> publishing
  │                     │                                        │
  │                     └──驳回──> rejected（回到 draft，可改）    ├──成功──> published
  └──取消──> cancelled                                            ├──部分成功──> partially_published
                                                                  └──失败──> failed（可重试）
```

- **每个平台独立状态**，一个平台失败不影响其他平台（截图里的"2/7 平台已发布"就是这种语义）。
- `published` 之后**不可回滚**，只允许"删除/隐藏"（且部分平台不支持），所以 UI 必须在提交前做强确认。

#### 5.4.2 幂等的三层保证

1. **业务幂等键**：`(content_version_id, platform)` 唯一。同一版本的同一平台只允许存在一个"进行中"的任务。
2. **请求幂等键**：调用平台接口时带 `idempotency_key`（UUID v4，落库）。网络超时后重试时复用同一个 key，避免"其实成功了但又发一遍"。
3. **平台回执核对**：不确定状态（超时/5xx）时，先**查询**（如 B 站稿件列表、公众号已发布列表）确认是否已存在，再决定是否重发。
   > 这是发布系统最容易出事故的地方：**永远不要在网络超时后直接重试发布**，一定要先查后发。

#### 5.4.3 调度实现

- 定时任务用 **Celery beat + Redis**（MVP 足够）；任务量上来或需要可视化工作流时再换 Temporal。
- 到点触发的精度设为 **±60 秒**即可，不需要秒级。
- **发射窗口保护**：同一账号同一平台 5 分钟内不允许两个发布任务（平台侧容易判定异常，也可能触发"发布过于频繁"）。
- **补偿扫描**：每 5 分钟扫一次 `scheduled` 且 `scheduled_at < now - 2min` 的任务，防止 beat 漏触发。

#### 5.4.4 发布内容的"平台适配"

一条内容在四个平台不是同一份 payload：

| 平台 | 标题 | 正文 | 封面 | 特殊 |
|---|---|---|---|---|
| 抖音 | 文案 ≤ 55 字可见 | — | 竖版 9:16 | 话题、@、位置 |
| B 站 | 标题 ≤ 80 字 | 简介 | 16:9 | 分区 tid、标签、充电、定时 |
| 小红书 | 标题 ≤ 20 字 | 正文 ≤ 1000 字 | 3:4 | 话题、地点 |
| 公众号 | 标题 ≤ 64 字 | 富文本 | 2.35:1 | 作者、摘要、原文链接 |

因此数据模型里必须是 **`content`（母版）+ `content_variant`（平台变体）**，而不是一条内容四个字段。
发布前要有"**平台预检**"：字数超限、封面比例不符、敏感词命中、必填项缺失——**在提交前拦住，而不是等平台报错**。

### 5.5 评分与建议模块的实现方式

- **离线批处理**：每日 03:00 跑 T+1 评分，写入 `score_snapshot`（带 `algo_version`）。
- **在线只读**：API 只读最新版本快照，**不做实时计算**（否则首页会被算法拖慢）。
- **可重跑**：算法升级后，按 `algo_version` 重算历史，页面可对比"v1 vs v2 打分差异"（这是建立信任的关键功能）。
- **规则引擎与算法分离**：
  - 评分 = 统计计算（§6），输出三个分 + 分位 + 明细。
  - 建议 = 规则引擎，输入是评分结果与指标，输出"结论 + 证据 + 动作"（§6.6）。
  - LLM 只做**措辞润色**，**不允许产生数字**。所有数字必须来自引擎，并带 `evidence` 字段可点开核对。

## 6. 算法评分设计（重点）

### 6.1 设计原则

1. **先可比，再打分。** 四平台指标口径不同（抖音"播放"、小红书"阅读/观看"、公众号"阅读数"、B 站"播放"），必须先映射到统一语义，再谈分数。
2. **比率优先，绝对量辅助。** 10 万粉的号和 1000 粉的号比"点赞数"没有意义，比"点赞率"才有。
3. **每个平台一套权重，不搞"统一公式"。** 强行统一会让某一平台系统性吃亏（例如公众号天然低互动率）。
4. **可解释。** 任何分数都能拆到"哪几个指标、贡献多少、和谁比"。
5. **抗噪。** 样本少时要收缩，异常值要剔除，否则一条 100 播放的视频会让整个账号评分失真。

### 6.2 指标字典（统一语义层）

| 统一指标 | 抖音 | B 站 | 小红书 | 公众号 |
|---|---|---|---|---|
| `exposure` 曝光 | 展示量（后台） | 曝光（部分可见） | 曝光 | 送达人数 |
| `view` 消费量 | 播放数 | 播放数 | 阅读/观看数 | 阅读数 |
| `completion` 完成率 | 完播率 | 完播率 | 阅读完成率 | 阅读完成率 |
| `like` | 点赞 | 点赞 | 点赞 | 点赞 |
| `comment` | 评论 | 评论（含弹幕单列） | 评论 | 留言 |
| `save` | 收藏 | 收藏 | 收藏 | 收藏 |
| `share` | 分享 | 分享 | 分享 | 分享/转发 |
| `follow_gain` | 涨粉 | 涨粉 | 涨粉 | 净增关注 |
| `profile_visit` 主页访问 | 主页访问 | 空间访问 | 主页访问 | —（用"阅读→关注"替代） |
| `neg_feedback` 负反馈 | 不感兴趣/举报 | 拉黑/举报 | 举报/不感兴趣 | 取关 |

**派生比率（真正参与打分的）**

```
view_rate      = view / exposure            # 封面/标题吸引力
completion     = 完成率                      # 内容质量核心
interaction    = (like + comment + save + share) / view
save_rate      = save / view                # "有用"信号，最抗刷
comment_rate   = comment / view             # "有话说"信号
share_rate     = share / view               # "愿意背书"信号
follow_rate    = follow_gain / view         # 转化核心
profile_rate   = profile_visit / view       # 兴趣强度
neg_rate       = neg_feedback / view        # 风险信号
```

> 注意：不同平台的 `interaction` 分母不同（抖音习惯用播放，公众号习惯用阅读），**必须统一到 `view`**，否则跨平台分数不可比。

### 6.3 归一化：四步流水线

**Step 1 · 对数压缩**
绝对量指标（播放、涨粉）先做 `x' = ln(1 + x)`，避免头部内容把分布拉爆。

**Step 2 · 组内分位**
在**同平台、同内容形态（视频/图文）、同账号规模档位**的参照池里算百分位：
```
p = percentile_rank(x', pool)
```
参照池优先用**自己账号的历史内容**（≥ 30 条后启用）；不足时退化到"平台公开基准值"（人工维护的一张基准表，按粉丝量档位分桶）。
→ 这一步解决了"跨平台可比"：分数表达的是"在你这个平台、这个体量里，你排第几"，而不是绝对数值大小。

**Step 3 · 小样本贝叶斯收缩**
```
score_raw = 0.6 * p_completion + 0.2 * p_save + 0.1 * p_comment + 0.1 * p_share   # 以质量为例
score = (n / (n + k)) * score_raw + (k / (n + k)) * prior
```
- `n` = 该指标的有效样本量（如播放量达到阈值的比例，或内容条数）
- `k` = 平台平滑系数：抖音 8、B 站 6、小红书 10（数据噪声大）、公众号 3（发布少、单篇权重大）
- `prior` = 该账号近 90 天的中位数分，新账号用 50

**Step 4 · 时间窗对齐**
每条内容只在**固定观察窗**（24h / 72h / 7d）取数，**不同内容用同一个窗对比**。
禁止"这条取 30 天、那条取 3 天"——这是最常见的评分失真来源。

**异常剔除（在 Step 2 之前）**
- 播放 < 平台阈值（如抖音 < 100、B 站 < 50）的内容标记 `insufficient`，不参与分位计算，但仍在列表展示。
- 单指标 > 组内 P99 且伴随 `neg_rate` 异常升高的，标记 `suspect`（疑似刷量/被推流），单独成组。
- 发布 72h 内被删除的内容不参与评分（避免"删掉差内容"刷分）。

### 6.4 三个分：质量 / 转化 / 互动

#### 质量分 Q（内容本身好不好）

| 平台 | 权重构成 |
|---|---|
| 抖音 | 完播 0.40 · 平均播放时长分位 0.20 · 收藏率 0.20 · 分享率 0.10 · 负反馈（反向）0.10 |
| B 站 | 完播 0.30 · 收藏率 0.25 · 投币率 0.15 · 弹幕/评论率 0.15 · 分享率 0.15 |
| 小红书 | 阅读完成率 0.35 · 收藏率 0.30 · 点赞率 0.20 · 分享率 0.15 |
| 公众号 | 阅读完成率 0.40 · 在看率 0.25 · 收藏率 0.20 · 转发率 0.15 |

#### 转化分 C（能不能把人变成粉丝/客户）

| 平台 | 权重构成 |
|---|---|
| 抖音 | 涨粉率 0.50 · 主页访问率 0.30 · 搜索/同城来源占比 0.20 |
| B 站 | 涨粉率 0.55 · 空间访问率 0.25 · 追番/系列转化 0.20 |
| 小红书 | 涨粉率 0.60 · 主页访问率 0.25 · 私信/评论咨询率 0.15 |
| 公众号 | 阅读→关注率 0.60 · 原文链接点击率 0.25 · 菜单/关键词回复率 0.15 |

> 公众号没有"主页访问"，用"阅读→关注"作为等价物；这是**唯一必须做平台特化**的地方。

#### 互动分 I（有没有人愿意说话）

```
I = 100 * (0.45 * p_interaction + 0.30 * p_comment_rate + 0.25 * p_velocity)
```
- `p_interaction`：总互动率分位
- `p_comment_rate`：评论率分位（比点赞更抗刷）
- `p_velocity`：**互动速度**——发布后前 3 小时互动量 / 该账号历史同期中位数。这是识别"被推荐"的关键信号，很多工具都不做。

#### 总分

```
Total = 0.40 * Q + 0.30 * C + 0.30 * I
```
`Q/C/I` 各自再做一次平台内分位，保证三个分在同一量纲（0–100）。
**为什么不给用户调权重**：第一期固定，避免"调参调到分数好看"；第二期可提供"内容目标"预设（涨粉优先 / 品牌优先 / 互动优先），本质是三套固定权重。

### 6.5 账号健康度（日级）

内容分是"点"，账号需要"面"。建议每天算一个 `AccountHealth`：

```
Health = 100 - 100 * Σ (w_i * max(0, z_i))
```
其中 `z_i` 为以下指标的标准化偏离度（相对自己近 28 天基线）：
- 净涨粉为负的天数占比（权重最高）
- 互动率环比下滑幅度
- 发布断档天数（超过计划频率）
- 负反馈率上升
- 采集失败导致的数据缺口（数据不可信时健康度也要打折）

输出为三档：`稳健 / 需关注 / 异常`，只在 M0 和 M6 露头，不在首页放大——**健康度是预警工具，不是荣誉勋章**。

### 6.6 改进意见怎么生成（规则引擎，不是"AI 打分"）

**架构**：`指标事实 → 规则匹配 → 证据组装 → 模板渲染 →（可选）LLM 润色`

规则用声明式配置（YAML/JSON），不写死在代码里：

```yaml
- id: R_DY_LOW_COMPLETION
  platform: douyin
  when:
    all:
      - metric: completion_percentile
        lt: 35
      - metric: view
        gte: 1000          # 样本足够才提示
  severity: high
  conclusion: "完播率处于近 30 条内容的低位（P{{completion_percentile}}），前 3 秒流失明显"
  evidence:
    - "完播率 {{completion}}%，账号中位数 {{median_completion}}%"
    - "同类内容平均完播 {{benchmark}}%"
  actions:
    - "把钩子前置到 0–3 秒，首帧直接给结论/冲突"
    - "时长从 {{duration}}s 压到 30s 以内再测一条"
  confidence: 0.8
```

**规则分层（建议先做 20 条左右）**

| 层 | 规则类型 | 示例 |
|---|---|---|
| L1 异常检测 | 环比/分位突变 | 掉粉加速、播放腰斩、互动率异常升高 |
| L2 归因 | 指标间关系 | 曝光正常但点击率低 → 封面/标题问题；点击高但完播低 → 开头问题 |
| L3 对比 | 跨平台/跨内容 | 同一作品 B 站完播 62%、抖音 18% → 平台适配问题 |
| L4 结构 | 分布/节奏 | 发布时间与互动速度的关系；连续 5 条低分 → 选题疲劳 |
| L5 建议 | 动作模板 | 基于最低分维度给出 1–3 条具体动作 |

**归因规则是价值核心**，举个完整例子：

```
事实：exposure 正常（P60）→ view_rate 低（P20）→ completion 正常（P70）
结论：不是内容问题，是"没人点"——封面/标题出了问题
动作：换封面 A/B（用同作品在 B 站的高点击封面做参考）
证据：曝光 12.3 万（P60）· 点击率 3.1%（P20，账号中位 6.8%）· 完播 41%（P70）
```

**LLM 的边界（写进规范）**
- 只允许改写 `conclusion` 与 `actions` 的措辞，让它更像人话。
- **禁止**生成任何数字、禁止新增规则未命中的结论。
- 输出必须带 `rule_id` 与 `evidence`，UI 上"怎么算的"可展开。
- LLM 失败时自动回退到模板文案（模板本身必须可读，不能是占位符）。

### 6.7 冷启动与样本不足

| 阶段 | 数据量 | 策略 |
|---|---|---|
| 0 条 | 刚接入 | 只显示原始数字，**不显示分数**，文案："积累 7 天数据后开启评分" |
| 1–10 条 | 首周 | 用平台基准表做分位，标注"基准：平台公开均值，置信度低" |
| 11–30 条 | 第 2–4 周 | 混合基准（50% 自有 + 50% 平台），置信度中 |
| > 30 条 | 稳定期 | 纯自有分位池，置信度高 |

**置信度必须在 UI 上可见**（一个 3 格小条或"低/中/高"标签）。没有置信度的评分会误导决策。

### 6.8 防作弊与自我欺骗

- 不把"删除差内容"当作优化（72h 内删除的内容仍计入统计）。
- 刷量识别：互动率 > P99 且 `view` 增长曲线呈阶跃、评论内容重复度高 → 标记 `suspect`，分数不计入账号均值。
- 跨平台搬运内容在 B 站可能被判低质，评分不应因此惩罚"选题"，只惩罚"该平台的适配度"（这是 L3 规则要处理的）。
- **算法变更留痕**：每次调整权重必须升 `algo_version`，并保留旧版本结果 90 天，避免"分数突然集体变化"引发的信任危机。

### 6.9 如何验证评分是"对的"

1. **人工标注 50 条**（好/中/差），算与评分的 Spearman 相关系数，目标 > 0.6。
2. **稳定性**：同一批内容隔 7 天重算，分数波动应 < 5 分（除自然增长外）。
3. **区分度**：Top 20% 与 Bottom 20% 的实际涨粉差，应显著大于 0。
4. **可解释性抽检**：随机抽 10 条洞察，人工判断"结论是否成立"，目标 > 80%。

## 7. 分期计划与风险

### 7.1 分期

> 不给时间估算，只给**交付物与前置条件**。每期结束必须能演示。

#### 第 0 期 · 立项与技术验证（不做产品界面）
**目标**：证明"数据拿得到"。
- 交付物：四个平台各一个最小采集脚本（仅取粉丝数 + 最近 5 条作品指标），跑通 3 天不中断；一份《数据可得性实测报告》。
- 关键动作：**立刻启动 B 站开放平台入驻与接口申请、公众号认证**（这两个周期最长，必须并行）。
- 通过标准：四平台中至少 2 个能稳定拿到 T+1 数据。
- **如果第 0 期失败，整个项目应降级为"手动记账 + 分析台"**，不要硬推。

#### 第 1 期 · 可用（MVP）
- 首页（M0–M6）+ 内容列表（M7）+ 单篇详情（M8，仅基础指标）。
- 采集：B 站走官方 API；其余走浏览器采集或手动导入。
- 评分 v1：仅 Q/I 两维（转化数据不足），置信度标注。
- 发布：**只做公众号 + B 站**，其余生成"发布包"。
- 通过标准：每天早上能在 3 分钟内看完并做出一个决策。

#### 第 2 期 · 好用
- 发布编排（M9）完整状态机 + 预检 + 重试。
- 评分 v2：三维分 + 平台权重 + 规则洞察 20 条。
- 平台对比（M10）、内容排行多维筛选。
- 数据质量看板、采集告警。

#### 第 3 期 · 有判断力
- 归因规则（L2/L3）与建议动作库。
- 画像（M11）与流量来源（M12）——取决于数据可得性。
- 周报自动生成与导出。
- 评分 A/B：同一选题不同封面/开头的对照实验。

### 7.3 三条 B 计划（必须提前想好）

**如果官方接口全部拿不到：**
→ 产品定位改为"**多平台数据归集 + 分析**"：发布侧只做素材包与提醒；采集侧以浏览器插件为主。界面不变，卖点从"自动化"改为"统一口径与判断力"。这依然是有价值的产品。

**如果连浏览器采集也不稳定：**
→ 退化为"**周报导入**"：每周从四个后台导出 CSV/截图，系统做清洗、对齐、评分。采集成本接近 0，分析价值保留 80%。

**如果预算不足以买第三方数据：**
→ 小红书只做"公开笔记页低频抓取（点赞/收藏/评论）"，放弃画像与流量来源。UI 上直接写"该平台暂不提供此维度"，**不要用估算值填充**。

### 8.2 术语

| 术语 | 含义 |
|---|---|
| 内容 / content | 一个平台上的一条作品 |
| 作品 / work | 一稿多发的"母版"，下挂多个 content |
| 观察窗 / window | 发布后的固定取数时点（24h/72h/7d/30d） |
| 分位 / percentile | 在参照池中的排名百分位（0–100） |
| 置信度 | 样本量与数据完整性决定的分数可信程度 |
| 采集 / collect | 通过 API 或浏览器获取数据的行为 |
